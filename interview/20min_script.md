# 20 分钟项目讲解稿：知行数字运维专家

## 1. 项目背景

这个项目面向地铁运维场景。现场人员处理故障时，通常要在规范库、设备台账、告警系统、工单系统、API 和图纸资料之间来回查询。传统做法的问题是信息分散，而且一个问题往往不是单一检索，例如现场人员会直接问：

> 查一下某条规范要求，再看某个风机最近三天告警次数，并判断是否需要停机检查。

它同时包含静态规范检索、实时数据查询和故障建议，单纯做一个 RAG 问答并不能完整解决。

我的工作重点是意图识别、工具调用链路、混合检索、拒答和评测，其中最核心的是多意图问题如何拆解和执行。

## 2. 总体架构

整个链路可以分为六层：

1. 输入标准化：统一规范编号、破折号、设备别名和时间表达；
2. 意图规划：把问题拆成一个或多个原子子任务；
3. 计划校验：检查意图与工具映射、参数完整度、权限和依赖关系；
4. 工具执行：规范走 Hybrid 检索，实时数据和工单走 NL2API，图纸走结构化图纸检索；
5. 结果充分度：判断结果是否覆盖所有子问题、设备和时间是否匹配；
6. 答案汇总：事实、规范依据和处理建议分开输出，并保留来源。

LangGraph 主要负责保存状态和固定执行流程。状态中不只存消息，还存标准化问题、子任务列表、工具结果、重试次数、错误和最终证据。

## 3. 为什么不能只做单标签分类

早期版本让模型在规范查询、设备查询、工单查询、图纸查询和故障诊断中选一个标签。单意图没有问题，但多意图场景会出现漏识别。

例如：

> 查 JTG D81-2017 的应急照明要求，再统计 A12 风机最近三天告警次数，并给处理建议。

单标签可能只输出规范查询，后续只调用知识库。即使答案里给了处理建议，也没有设备数据支持。

因此我把输出从一个标签改成结构化计划。每个子任务包含：

- task_id；
- intent；
- tool；
- query；
- entities；
- slots；
- missing_slots；
- depends_on；
- condition；
- confidence。

这个问题会被拆成：

- T1：规范检索，调用 `hybrid_search`；
- T2：告警统计，调用 `nl2api_query`；
- T3：故障建议，不直接调工具，依赖 T1 和 T2。

T1 和 T2 并行，T3 等两者完成后再汇总，这样既降低延迟，也保证建议有证据。

## 4. 工具边界

### Hybrid 检索

用于规范、手册和检修规程。主链路是 Elasticsearch BM25 和 Milvus 向量召回，再通过 RRF 融合和 BGE-Reranker 精排。

静态规范问题不能调用实时 API。例如“JTG D81-2017 的照明要求”应该只查规范库。

### NL2API

用于设备台账、运行指标、告警次数和工单数据。模型不直接执行任意 SQL，而是先输出受限结构：domain、operation、filters、metrics、group_by 和 time_range，再由后端转换成只读 SQL 或内部 API 请求。

写操作、删除工单和远程启停设备不允许执行。

### 图纸检索

图纸先通过 Qwen2.5-VL 抽取表格、图号、设备编号和关键字段，再建立可检索字段。用户查接线图或图纸中的控制柜编号时调用 `drawing_search`。

## 5. 多意图的判断原则

我没有看到“和、再、同时”就机械拆分，而是判断是不是独立可执行目标。

例如：

- “风机设备规范和检修要求”仍然是一个规范检索；
- “A12 风机状态和告警信息”可以用一次设备查询完成；
- “查规范，同时统计告警次数”是两个不同数据源，必须拆成两个工具任务；
- “查询状态，如果振动超过阈值再查规范”属于条件执行，不是简单并行。

同一个工具的多个意图还要考虑合并。例如状态和当前告警信息可以在一次 API 请求中返回，避免重复调用。

## 6. 信息不完整怎么处理

我们主要检查设备、时间、图号、规范版本和指标是否完整。

例如：

> 查一下它最近报警几次。

这里“它”没有明确指向，不能根据模型感觉猜设备编号。系统会输出 `needs_clarification=true`，只询问具体设备。

再例如：

> A12 风机报警多少次？

设备有了，但没有时间范围。告警次数是时间窗口相关指标，因此需要补充是今天、最近三天还是最近一个月。

澄清发生在工具执行之前，避免先查错数据再浪费一次调用。

## 7. 条件调用怎么做

例如：

> 先查 A12 风机最近三天振动值，如果超过 4.5mm/s 再查检修规范。

计划中先创建 API 查询任务，再创建规范检索任务，并让规范任务依赖 API 任务。执行器读取上游结构化结果，提取振动值，与 4.5 比较，满足条件才继续调用知识库。

这里不能只让大模型在自然语言中自己判断，因为工具调用是否发生需要可审计，所以阈值比较由代码执行。

## 8. 典型 Bad Case 与修复

### Bad Case 1：否定范围

“不要查规范，只查设备状态。”

早期版本看到“规范”仍会调知识库。修复是在分类前识别否定范围，把被否定的意图从候选中移除。

### Bad Case 2：引号关键词

“‘查询规范’这个按钮是什么意思？”

这里是在讨论按钮，不是真正查规范。分类时先把引号内容替换成占位符，避免关键词误触发。

### Bad Case 3：时间冲突

“最近三天，也就是 8 月 1 日到 8 月 2 日。”

相对时间和绝对时间不一致，系统不选其中一个，而是澄清。

### Bad Case 4：领域词碰撞

“查规范中‘工单’一词。”

“工单”是文档关键词，不是工单系统查询。需要结合句法范围，而不是只看关键词。

## 9. 评测集怎么做

如果正式做 200 条人工评测，我会按场景分层抽样，而不是随机堆问题：

- 单意图：规范、设备、工单、图纸；
- 多意图：双意图、三意图、同工具多意图；
- 参数缺失：设备、时间、图号；
- 条件执行：阈值、先后依赖；
- 否定与冲突：不要查、时间冲突、引号关键词；
- 安全边界：删除工单、控制设备；
- 无需工具：普通解释和闲聊。

每条标注以下字段：

- gold_intents；
- gold_tools；
- tool_args；
- needs_clarification；
- plan_mode；
- expected_dependencies；
- answer_coverage。

至少两个人独立标注，冲突样本由第三个人仲裁。对规范版本、设备别名和时间范围先制定统一标注说明，避免标注员口径不一致。

## 10. 指标

我不会只报一个“意图准确率”，因为多意图问题用单标签准确率不合适。主要指标包括：

- 意图集合完全匹配；
- 意图 micro-F1；
- 工具集合完全匹配；
- 工具参数准确率；
- 漏调率和过调率；
- 澄清判断准确率；
- 并行、串行和条件执行准确率；
- 端到端任务成功率。

对 Bad Case 还要记录错误类型，例如漏意图、工具错误、参数缺失、参数幻觉、错误顺序和不必要澄清。

## 11. 项目边界

当前复现包使用模拟数据和规则路由，目的是复现工程链路和评测方式，不等同于完整生产系统。真实上线还需要：

- 接入真实 Elasticsearch、Milvus、设备 API 和图纸库；
- 模型路由与规则 Guardrail 做 A/B 测试；
- 加入权限、审计、超时、重试和熔断；
- 对真实 200 条数据复测；
- 监控输入分布漂移和新型 Bad Case。

## 12. 三分钟精简表达

> 这个项目是面向地铁运维的 RAG/Agent 系统，核心问题是现场人员的一句话经常同时包含规范查询、设备数据查询、工单查询和处理建议。早期我们用单标签意图分类，一次只能输出一个意图，多意图问题会漏调工具。后来我把路由改成结构化任务规划：把问题拆成原子子任务，每个任务包含意图、工具、参数、缺失槽位和依赖关系。规范走 Hybrid 检索，设备和工单走只读 NL2API，图纸走结构化图纸检索。独立查询并行执行，处理建议依赖前面证据，条件任务由代码判断阈值后再决定是否调用下一个工具。除此之外，我还做了否定范围、引号关键词、时间冲突和缺参数的 Guardrail。评测时不只看意图准确率，还看工具集合、参数、澄清、执行顺序和端到端覆盖，这样可以把 Bad Case 定位到具体模块。
