# 高频追问与回答

## 1. 为什么不直接让大模型 Function Calling？

> Function Calling 能输出工具名和参数，但它本身不能保证多意图一定拆全，也不能保证调用顺序、参数完整和安全边界。所以我在模型输出外面加了一层结构化 Plan 和 Validator。模型负责理解语义，代码负责 Schema 校验、依赖检查、阈值判断、权限和重试。这样比完全自由的 Agent Loop 更可控，也方便做离线评测。

## 2. 多意图为什么不直接多标签分类？

> 多标签只能告诉我有哪些意图，但不能表达每个意图对应的参数、工具、依赖和条件。例如“如果振动超过阈值再查规范”，只知道设备查询和规范查询两个标签还不够，还要知道谁先执行、阈值是多少、后一个任务的触发条件是什么。所以最终使用的是任务规划结构，而不是只有标签集合。

## 3. 多个工具什么时候并行？

> 只有互不依赖时才并行。例如规范检索与告警统计来自不同数据源，可以同时执行。故障建议依赖两者，必须等结果回来。条件查询必须先执行上游，不能并行。实现上可以使用 asyncio 或线程池处理 I/O 型工具，并通过 task_id 和 depends_on 管理依赖。

## 4. 如何避免重复调用同一个工具？

> 在 Validator 中按工具、实体、时间和指标做任务合并。如果用户问“A12 风机状态和当前告警”，一次设备 API 就能返回，不需要拆成两个请求。如果问“A12 风机工单和告警趋势”，虽然都走 NL2API，但背后域和聚合逻辑不同，可以并行执行两个只读查询。

## 5. 怎么判断信息不完整？

> 不是让模型主观判断，而是按意图定义必需槽位。告警次数至少需要设备和时间；工单历史需要对象和时间；图纸查询需要图号、设备编号或足够具体的图纸关键词。缺少关键槽位时进入 clarify，不执行工具，也不补默认值。

## 6. 为什么要单独做 Validator？

> Router 的错误主要来自语义理解，Validator 负责确定性规则，例如意图和工具映射、必需参数、只读权限、依赖是否成环、是否重复调用。把两者分开后，Bad Case 更容易定位，也能避免模型一次输出错误就直接触发业务接口。

## 7. 61% 到 78% 是怎么定义的？

> 面试时必须先说明口径。比较合理的口径是端到端路由成功率：意图集合正确、工具选择正确、关键参数正确，并且该澄清时没有执行工具。不能只说单标签准确率。具体数字必须来自固定的 200 条人工标注集，同一模型、同一 Prompt、同一温度和同一评测脚本复测。

## 8. 200 条评测集如何保证质量？

> 先制定标签定义和边界案例说明，再由两人独立标注，冲突样本仲裁。数据按单意图、多意图、缺参数、条件、否定、安全和无需工具分层。还要防止同模板改几个设备编号造成数据重复，训练或 Few-shot 示例不能泄漏到测试集。

## 9. 工具调用失败怎么办？

> 每个工具设置超时、最大重试和错误码。超时可以有限重试，参数错误回到 Validator 修复，空结果进入充分度判断。多个工具中只有一个失败时，保留成功结果并明确未完成部分；关键证据缺失时不输出确定性诊断。

## 10. LangGraph 在这里的价值是什么？

> 我把 LangGraph 当作可控编排层，不是让它替代业务逻辑。它负责保存 Plan、工具结果和错误状态，固定 Router、Validator、Executor、Sufficiency 和 Synthesizer 的流转，并支持条件分支。真正的参数校验和工具权限仍由代码实现。
