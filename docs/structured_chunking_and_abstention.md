# 结构化切分与拒答闭环

面向非本项目人员的说明。所有数字来自 `outputs/overnight_vertical_slice_report.json`。

## 1. 为什么不按固定 token 切

固定长度切分是按**字符数**下刀，而字符数和**意思**没有关系。它会：

- 把条款编号和条款正文切开——编号没有正文答不了，正文没有编号引不了；
- 把某台设备的数据行和它的表头切开——`45kW` 单独存在时，没人知道它是功率还是风量；
- 把两台设备的数字揉进同一块——`A16 45kW A17 55kW`，之后谁也分不出哪个属于谁。

关键在于：**这三件事一旦切坏，后面任何检索器都救不回来**，因为"谁的、什么字段"这层关系已经不在文本里了。

所以顺序必须反过来：**先恢复"这是什么、属于谁"，再决定在哪里下刀。** 只有普通正文超过预算时才二次拆分，且在句子边界处切。

## 2. 多级表头怎么处理

把每一列的表头展开成一条**路径**：

```
["参数", "功率"]      ["参数", "风量"]      ["备注"]
```

合并单元格的处理是关键。表头第一行 `["设备","参数","","备注"]` 里那个空白，是 `参数` 横跨两列的结果；第二行 `["","功率","风量",""]` 的空白同理。空白要向左继承，**但只能在同一个父级下继承**。

本轮真实跑通时抓到的 bug：不加这个限制，`备注` 列会继承到左边的 `风量`，变成 `备注.风量`——之后一个查"风量"的请求会命中备注格。已修，并补了回归测试。

于是每行被写成：

```
风机参数表；设备A16；参数.功率=45kW；参数.风量=28000m3/h；备注=常用
```

而不是 `A16 45kW 28000m3/h`。后者回答不了"A16 的功率是多少"——里面没有任何东西说明哪个数字是功率。

## 3. bbox 有什么作用

三件事：

1. **可核对**。人能翻到第 3 页那个框，用眼睛确认系统读得对不对。
2. **可引用**。答案能说"依据第 3 页标题栏"，而不是"根据系统判断"。
3. **可局部重识别**。字段读错时，可以只对那一小块区域重新识别，不用重跑整页。

反过来说：**一个指不出位置的值不能作为证据。** 没人能核对它，答案也无法引用它。本轮的策略层把 `source_traceable` 作为硬性要求，没有页码的字段直接判为不可作答。

## 4. 图片处理完为什么能被 BM25 和向量库召回

因为到这一步它**已经不是图片了**。

解析链路把图纸变成结构化字段（图号、设备编号、功率……），切分层再把每个字段写成一条带上下文的文本：

```
图号 FAN-A16-01；设备 A16；功率 45kW
```

这是普通文本，BM25 能对它做倒排索引，向量模型能对它算 embedding。**图号、设备号这类精确标识符主要靠 BM25**——它们是字符串匹配问题，向量检索反而容易把 `A16` 和 `A17` 算得很近。**换了说法的自然语言查询主要靠向量**。两路各管一段，再融合。

## 5. 为什么 RRF 分数不是置信度

RRF 的公式是：

```
RRF(d) = Σ 1 / (k + rank_i(d))
```

它只用**名次**，完全不用两个检索器各自的分数。k=60 时，一个被两路都排第一的文档得分是 `2/61 ≈ 0.0328`。

这个 0.0328 的意思是"两路都把它放在最前面"，**不是"3% 可信"**。RRF 分数的取值范围由 k 和路数决定，跟正确概率没有任何关系。所以：

- 不能说 "RRF > 0.8 所以 80% 可信"——这个分数根本到不了 0.8；
- 不能拿它做阈值判断答案对不对；
- 它只能用来**排序**。

判断能不能作答是另一套东西（见第 8、9 条）。

## 6. 什么情况下补检索

证据缺的是**系统自己能找回来的东西**时：

- 目标字段没检索到 → 换查询重新混合召回；
- 检索到了但缺上下文（不知道是哪张表、哪一章）→ parent 扩展。

补救次数有上限（配置项 `max_remediation_rounds`，当前 2）。**没有上限的补救不是补救，是死循环**——一个读不出来的页面，重试一百次仍然读不出来，只是烧掉一百次的钱。

## 7. 什么情况下局部调用 VLM

字段在页面上存在、但当前来源读不出或读错时——比如印章盖住了控制柜编号那一格。这时用该字段的 bbox 裁出那一小块，只对它重新识别。

**本轮没有真实调用**。决策链路会走到这一步并记录 `local_vlm_reidentify:not_invoked`，接口是通的，但没有花钱调模型。报告里如实标注。

## 8. 什么情况下 partial

部分字段证据完整、部分不完整时。

要点是：**一个非必需字段缺失，不能否决那些本来完全可靠的字段。** 用户问"功率和控制柜编号"，功率有页码有 bbox 有值、控制柜编号没读到——正确做法是给出功率、明确说控制柜编号缺失，而不是整个请求拒答。

## 9. 什么情况下必须拒答

四种：

1. **关键字段存在未裁决的冲突**——OCR 说一个值、VLM 说另一个值。**两个都留着，一个都不选。** 默认信 VLM 这条假设在本项目的对抗测试里被证伪过：唯一一次真实冲突中，OCR 是对的、VLM 把 `5` 读成了 `S`。
2. **值明显非法**——比如控制柜编号读成了中文印章文字。
3. **补救次数用尽**仍然缺关键证据。
4. **高风险字段冲突** → 不是拒答而是**转人工**。一个错的控制柜编号会让人去动错的设备，这种情况不能只是沉默，必须有人来看。

拒答结果必须说清楚缺什么：

```json
{
  "decision": "abstain",
  "answerable_fields": {"功率": "45kW"},
  "missing_fields": ["控制柜编号"],
  "reason_codes": ["REQUIRED_EVIDENCE_MISSING"],
  "evidence_refs": [{"document_id": "drawing_001", "page": 3, "bbox": [120, 340, 930, 410]}]
}
```

**只回"置信度不足"是不合格的**——用户不知道缺了什么，也不知道该补什么。

## 10. 目前最大的三个限制

**一、没有接真实的 ES / Milvus / Reranker / 实时 VLM。**
BM25 是真实算法但跑在进程内，不是 Elasticsearch。向量侧是一个**声明式的确定性替身**，没有 embedding 模型——它不建模同义词，只做加权 token 重叠。所有这些在报告里都标了 `not_connected` / `real_model: false`。任何"完成了 ES/Milvus 联调"的说法都是假的。

**二、没有独立的检索 gold，所以没有 Recall@5。**
本仓库没有人工标注的"这个查询应该召回哪些 chunk"。从系统自己的输出反推一份 gold，算出来的召回率是循环论证。报告里这一项写的是 `NOT COMPUTED` 加上原因，不是一个数字。

**三、中文按字切分导致"无匹配"查询仍会返回结果。**
本轮实测：查询 `完全不存在的查询词组合` 仍返回 3 条，因为它和条款文本共享「的」「组」「合」这些常用字。没装中文分词器，字级 unigram 是可辩护的默认，但代价就是这个。**我没有加一个分数下限把它盖掉**——那是看到输出之后调参。如实记为限制，留作下一轮。
